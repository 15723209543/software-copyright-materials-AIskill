# 软件著作权申请资料生成 Skill v1.0

## 0. 必须先遵守的输出契约

收到**完整程序源码包 ZIP 或源码目录**，默认生成且只交付：
1. `<软件名>_<版本>_程序鉴别材料.docx`；
2. `<软件名>_<版本>_软件说明书.docx`；
3. `<软件名>_<版本>_官网填报信息.md`。

可把以上三份放在一个结果 ZIP；QA 预览图、源码清单、分析 JSON、校验报告为工作文件，默认不混入交付 ZIP。无完整源码不得假装已经完成三份申请材料。不能捏造用户姓名、权属、首次发表时间、研发时间、真实运行截图、软件功能或源码。**绝不把示例项目数据写进正式项目。**

## 0.1 申请信息必须从每次用户发送的指令读取

**与 `make-readme-and-license` Skill 一样：调用模板本身带完整的可填写表单。** 外层文件 `调用模板_Codex.md`、`调用模板_网页版GPT.md` 包括软件名、版本、是否发表、开发方式、开发完成日期、申请人/登记办理人、著作权人及联系人、权利归属、代理信息、学校/单位情形、截图库等字段。用户填写的信息是本次任务的法律事实输入；Skill 内任何示例姓名、邮箱、版本都不是默认申请人资料。

执行时先读取调用消息的用户填写内容，映射到内存/临时 `project_analysis.json` 的 `official` 字典，再从源码补全**技术**事实。重复字段需要交叉核对，冲突直接标注。不能把既有 README 作者 `15723209543@163.com` 当成本次的软件申请人；也不要从 Git 提交者猜测著作权归属。如果未填写，则在官网 MD 中保留待确认标记，而不是为了得到表面完整的文档凭空填写。敏感证件号与联系信息默认只在官网填写；只有用户明确允许才在 MD 中出现。

详细映射见 `references/prompt-templates.md`。如用户一次上传了完整源码和填妥的调用消息，正常情况下直接生成三份结果，不要求用户重新重复输入同样信息。

## 1. 处理次序（必须按顺序）

1. 收集本次用户上传的全部源码 ZIP/目录，确认是完整项目，必要时检查多个包的关系；安全解包，不执行未知源码。
2. 运行 `scripts/source_inventory.py`，统计源码路径、原始行数、语言、哈希、疑似入口。忽略 Git、node_modules、虚拟环境、编译缓存、依赖库、minified 文件；关键功能若在被过滤目录，应人工复核、显式纳入。只读分析，不能执行恶意/不受信任项目。
3. 逐模块阅读真实代码，理解启动流程、用户可见页面与按钮、接口、数据库/本地数据、主要业务链路、异常处理，逐项记录**源码路径证据**，区分“代码中存在”“已运行验证”“未找到证据”。允许引用项目本来的 README 和部署文档作次要证据。
4. 先核对本次调用消息中的填写字段并将其准确映射到 `official`（个人/权属信息只能由用户提供）。再结合 `references/example-style.md` 和用户给的历史软件说明书组织内容，再生成 `assets/project_analysis.example.json` 同结构的**真实** `project_analysis.json`。逐项写实，不得套模板虚构功能。若需求说明来自用户但源码尚未实现，不能将其写成已实现功能。
5. 根据 `references/source-identification.md` 创建程序鉴别 Word；根据 `references/manual-style.md` 创建说明书 Word；根据 `references/official-form-checklist.md` 创建 R11 申请辅助填报 Markdown。
6. **先生成前三份核心材料再拓展**。生成后立即实际渲染 Word → PDF 供内部校验；检查每个代码页至少50行非空真实源码、文档无溢出/大留白/不合规尾页，手动核对抽样页。检查正式说明书第4章每一操作有独立 `【截图提示：图4-x，截取……】`。
7. 软件名称、版本、接口、模块数、源程序总量、开发环境在三份材料中统一；对代码无法说明的法律信息，在官网 MD 标注【待申请人确认】。若缺失关键数据应说明阻塞，不要伪装为提交版。
8. 仅当校验通过，使用 `scripts/package_result.py` 打包三份交付文件。最终告知哪些字段和截图仍需本人补齐，**不可宣称材料已经官方审核通过**。

## 2. 程序鉴别 Word：硬性规则

- 所有源码正文（含数字、括号、代码关键字）均 **宋体**；每个源码文件开始处必须用**黑体二号（22pt）**写明项目相对路径和真实文件名，如“代码文件：back/main.go（源文件第1行起）”。
- 不能有页眉、页脚，不能出现“第1/60页”等装饰性页标题。**整个代码 Word 第一页直接进入源码**，无独立封面。
- 每个物理页面至少 **50 行真实非空源码**；按 A4 排版，正文段前后 0pt，等距紧凑，页内无大块空白。第一个文件之后也遵守路径标题规则，不能丢掉函数/文件边界信息。
- 常规交存：按《计算机软件著作权登记办法》要求，原始完整源程序顺序中的前、后各连续30页，不足60页全部提交；不能随机抽取几十个文件然后自称“连续”。基于确定的文件顺序形成源码序列，较长项目通常用首尾各1500行（每页50行）构成60页；不满3000行则全部纳入。代码必须真实、保序，不添加伪代码、废话注释、隐藏行或复制凑行数。
- 若项目不足50行，或因极端长行/多标题无法在实际Word排版中保证每页50行，**报告无法达标，而不是造假**。代码行号只是便于核对源文件位置的排版序号，不计作伪造源码。长行不可截断或悄悄省略，必须调整字号、换行策略并核对。
- 50行/页是本用户的强制偏好，也符合一般规定下限；最终交存所需形式、页眉页码等要求以申请时所选办事渠道当前要求为准，若与“不要页眉页脚”的偏好冲突，必须主动指出，不能谎称两者同时符合。
- 辅助脚本只保证预排版、初步逐页统计；使用 `scripts/validate_materials.py` 在实际 Word 渲染后检查，不得仅数 DOCX 的段落声称物理页面满足要求。

## 3. 软件说明 Word：严格遵循历史风格

第1章软件概述，第2章总体结构，第3章源码目录/运行环境，**第4章软件界面与用户操作流程**，第5章起根据真实项目写前端交互、后端接口、数据组织、异常与维护。除用户另有要求，不要无意义的概念科普、算法教材知识、宣传或泛泛而谈的5—9章。

**第4章是重点**：通常至少写10个真实、独立、可证实的具体操作功能（若项目真实功能不足10项，应如实说明，不可凭空补足）；每项包含入口、前置条件、操作步骤、交互状态/执行结果、失败提醒、对应源码文件；每项**明确提供 `【截图提示：图4-x，打开……页面，完成……操作后截取……区域，必须显示……】`**。只做醒目的占位文字，不生成虚构截图，也不放大量白色图片框。

整体中文、宋体正文、黑体标题；Word 正文可以有必要表格和目录。版本/路径/端口/界面按钮必须从源码核验，不应照抄历史例子。非 Web 软件按真实 UI/命令行/设备操作重新组织第4章，不硬套“网站登录”。

## 4. 官网 MD：宁多勿漏

以“R11 计算机软件著作权登记申请”为默认，完整列出常见软件基本信息、研发日期、发表信息、开发方式、权利取得与范围、著作权人和联系人、软硬件及开发运行环境、编程语言/框架/数据库、代码量、主要功能/技术特点、上传附件、签章、代理、学校/单位归属及申报后跟踪事项。字段按**实际必填 / 条件适用 / 可选待核验**区分；网页当前标签和字数限制需要申请时实时核对，不能将第三方表格误称为官方最新表单。

对技术事实优先从源码提取；对姓名、证件、单位地址、时间及权属先读取本次调用消息；没提供的不能从代码猜测，使用 `【待申请人确认】`。用户要求保护的证件号用 `【请直接在官网填写】`。**不要默认作者邮箱就是著作权申请人或联系邮箱。** 对功能说明提供可以复制的中文正文，但不能夸大产品能力。详细见 `references/official-form-checklist.md`。

## 5. 脚本调用（Codex / 有 Python 运行环境）

```bash
python scripts/source_inventory.py --source "/path/project.zip" --out "/work/inventory.json"
# AI逐文件分析后，把 /work/project_analysis.json 填写为与真实源码一致的结构
python scripts/build_materials.py --inventory "/work/inventory.json" --analysis "/work/project_analysis.json" --output "/out/正式资料"
python scripts/validate_materials.py --report "/out/_build_report.json" --out "/work/qa_report.json" --preview-dir "/work/page_preview"
python scripts/package_result.py --report "/out/_build_report.json" --validation "/work/qa_report.json" --output "/out/软著申请资料.zip"
```

依赖：Python 3.10+、`python-docx`、`PyMuPDF`，以及用于逐页渲染的 LibreOffice（或者具备等效渲染验证能力的 Office 工具）。只有网页版 ChatGPT 时，由模型按本 Skill 的规则阅读源码并以平台提供的文档/运行环境生成文件；**网页版上传 ZIP 不等于安装 Skill**，如不可用 Python 或不能验证分页，必须披露限制，不得假报通过。

## 6. 文件与延迟读取

- `references/example-style.md`：实际用户历史说明书的章节和写法特点。
- `references/source-identification.md`：代码选取、排版、60页规则、物理页 QA。
- `references/manual-style.md`：软件说明书详细写作规范，第4章截图提示。
- `references/official-form-checklist.md`：官网字段、条件材料、法规链接及校验清单。
- `references/prompt-templates.md`：两平台消息调用模板。
- `assets/project_analysis.example.json`：生成前的事实分析数据结构，不得用示例内容替代实际内容。
- `assets/output-tree.example.txt`：交付物目录。

## 7. 完成条件

仅当三份文件存在、由真实源码支持、代码 Word 实际分页通过逐页核验、说明书第4章截图提示逐项完整、官网字段覆盖检查通过，才能报告“文档已生成并通过本地检查”。这**不等于**官方提交成功或审核通过。
